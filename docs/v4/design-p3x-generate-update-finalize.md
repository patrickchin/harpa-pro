# Design — Generate / Update / Finalize report flow

Status: **proposal**
Phase: P3.x (post-P3.8; refines the Edit-tab persistence + AI update
loop that P3.7 stubbed)
Touches: `packages/api`, `packages/api-contract`, `packages/ai-fixtures`,
`apps/mobile`

## 1 — Problem

The Generate Report screen has three user-facing actions:

1. **Generate report** — first-time AI run over notes
2. **Update report (N)** — re-run after new notes arrive
3. **Finalize report** — lock the draft

Today (post-P3.7):

- `services/ai.ts → generateReport()` only takes `notes` as input. So
  **"Update" regenerates from scratch and clobbers any manual edits**
  the user made in the Edit tab.
- The Edit tab persists changes to `localReport` (route component
  state) and **never** PATCHes them to the server. If the user edits
  the report, closes the screen, and reopens, the edits are gone. If
  the user edits then taps **Finalize**, the server finalizes whatever
  was last generated — not what the user saw.
- `notesSinceLastGeneration` is the only signal the action row uses to
  decide between "Update" vs "Finalize", but it tracks server state
  only — it can't see dirty local edits.
- `isAutoSaving` / `lastSavedAt` are declared in the provider props
  but never wired by the route.

This is a P3-era pitfall: a real default wiring is missing while the
surface looks like it works
([Pitfall 13](pitfalls.md#pitfall-13--di-stubs-become-the-spec-default-wiring-silently-broken)).

## 2 — Desired behaviour

User-visible contract:

> "Update report" re-runs the AI **using the existing report as
> context**, so manual edits are preserved (the model is told to
> merge new notes into the existing structured report rather than
> regenerate from scratch).
>
> Edit-tab changes are autosaved to the server. Finalize is only
> enabled once everything visible matches the server.

### Action-row state machine (target)

| Condition | Button |
|---|---|
| No report, no notes | "Generate report" *(disabled)* |
| No report, has notes | "Generate report" *(primary)* |
| Has report, `notesSinceLastGeneration > 0` | "Update report (N)" |
| Has report, no new notes, **autosave dirty/inflight** | "Saving…" *(disabled finalize)* |
| Has report, no new notes, clean | Regenerate icon + **"Finalize report"** |

### AI input contract

`generateReport()` gains an optional `existingBody`. When provided,
the user prompt embeds the existing report as `EXISTING REPORT:` JSON
and the system prompt instructs the model to **update** it — preserve
fields the user has hand-edited, integrate information from new notes,
do not regress filled-in values to null.

`/generate` (first time) sends `existingBody: null`.
`/regenerate` (Update) sends `existingBody: report.body` when the
server-side body is non-null.

## 3 — Changes by layer

### 3.1 `packages/api-contract`

- Extend `updateReportRequest` to allow patching `body`:
  ```ts
  export const updateReportRequest = z.object({
    visitDate: isoDateTime.nullable().optional(),
    body: reportBody.nullable().optional(),
  });
  ```
- No new endpoints. `PATCH /projects/{p}/reports/{n}` already exists.

### 3.2 `packages/api/src/services/ai.ts`

- `GenerateReportInput` gains `existingBody?: ReportBody | null`.
- A second system prompt — `REPORT_UPDATE_SYSTEM_PROMPT` — instructs
  the model to update the supplied existing report with the new notes
  while preserving manual edits. Selected automatically when
  `existingBody` is non-null. (Keep `REPORT_SYSTEM_PROMPT` for the
  cold-start case; do not break existing replay fixtures.)
- User prompt assembly: when `existingBody` is non-null, prepend
  `EXISTING REPORT:\n<minified JSON>\n\nNEW NOTES:\n…`.
- **Fixture impact**: a new fixture flavour
  `generate-report.update.*` per vendor (records the
  prompt + canonical response when an existing body is supplied).
  Cold-start fixtures (`full`, `incomplete`) are unchanged so
  existing tests don't move.

### 3.3 `packages/api/src/routes/reports.ts`

- `runGenerate()` already receives `ReportRow`. Pass
  `existingBody: report.body` to `aiGenerateReport()` from the
  **regenerate** handler. The generate handler passes `null`.
- `PATCH /reports/{n}` already calls `updateReport()`; extend the
  service so `body` flows through to the DB write.
- **No status transitions.** Finalize still requires `body !== null`,
  which is automatic since autosave will have persisted edits first.

### 3.4 `packages/api/src/services/reports.ts`

- `updateReport()` already takes a patch object; add `body` to the
  set of fields it persists. When `body` changes, **do not** reset
  `notesSinceLastGeneration` (that counter belongs to the AI loop,
  not manual edits).

### 3.5 `apps/mobile/lib/api/hooks.ts`

- Auto-regenerated by `pnpm gen:api`. The change in the contract
  schema flows through. Verify the generated `useUpdateReportMutation`
  invalidation still hits the report query key — declared in
  `invalidation.ts`, no code change expected there.

### 3.6 `apps/mobile` — Edit-tab autosave

New small hook `useReportBodyAutosave(slug, number, localReport)`:

- Debounce 800 ms after `localReport` changes (matches keystrokes
  → settle pattern used elsewhere).
- Skips when `localReport === lastSavedReport` (deep-compare via
  stable JSON or shallow ref check on slices).
- Calls `useUpdateReportMutation` with `{ body: toReportBody(localReport) }`.
- Exposes `{ isAutoSaving, lastSavedAt, error }`.
- On mount, seeds `lastSavedReport` from the server payload so the
  first dirty diff is the user's first edit, not the initial load.

Wire it inside `GenerateReportRoute`:

```ts
const autosave = useReportBodyAutosave(slug, reportNumber, localReport);
…
<GenerateNotes
  …
  isAutoSaving={autosave.isAutoSaving}
  lastSavedAt={autosave.lastSavedAt}
/>
```

### 3.7 `apps/mobile` — Action-row + Finalize guard

- `GenerateReportActionRow`: read `draft.isAutoSaving` and disable
  Finalize while autosave is dirty/inflight. Show a small "Saving…"
  pill in the row.
- `handleFinalize` in the route: if autosave is inflight, await it
  (or no-op + show inline notice). Simplest implementation: disable
  the button; rely on the autosave debounce + invalidation to flip
  it back to enabled.

### 3.8 Update-vs-regenerate UI

- Keep a single `handleRegenerate` callback. Inside it, pick the
  endpoint based on whether the current report has a server-side
  body:
  ```ts
  const endpoint = reportRow?.body ? regenerateMutation : generateMutation;
  ```
  (Already correct in the route; verify behaviour now that autosave
  ensures `body` is fresh.)
- The action-row label still branches on `hasReport` +
  `notesSinceLastGeneration`. Copy unchanged.

## 4 — Test plan (TDD order)

1. `services/ai.ts` unit — `generateReport({ existingBody })` builds
   the update prompt; selects the right system prompt; falls back to
   cold-start prompt when `existingBody === null`.
2. `services/reports.ts` unit — `updateReport({ body })` writes the
   new body, does not reset `notesSinceLastGeneration`,
   `updated_at` advances.
3. `routes/reports.integration` — `/regenerate` on a report with a
   body sends `existingBody`; `/generate` always sends null.
4. `routes/reports.integration` — `PATCH` with `body` persists,
   subsequent `GET` returns it. 409 if the report is finalized.
5. Mobile `useReportBodyAutosave` unit — debounces, skips no-ops,
   surfaces error, marks `lastSavedAt` on success.
6. Mobile `generate-report-tab.test` — Finalize disabled while
   autosave inflight; enables once `lastSavedAt` advances past last
   dirty edit.
7. Maestro flow — generate → manual edit a field → wait 1s →
   regenerate → confirm the edited field survives in the response.

## 5 — Rollout / migration

- No schema migration (`reportBody` already nullable on `reports.body`).
- New fixture set `generate-report.update.{openai,anthropic,…}` needs
  recording (live mode + `pnpm fixtures:record` against a real
  provider — see `arch-ai-fixtures.md`).
- Backwards compatible: clients that omit `existingBody` get the
  current cold-start prompt.

## 6 — Risks

- **Fixture recording cost.** A new flavour × N vendors. Mitigate by
  recording only the default vendor first; per-vendor lands as a
  follow-up.
- **Autosave races.** Two PATCHes in flight at once would clobber.
  Mitigate via React Query's `useMutation` queue (sequential) +
  `mutationKey: ['reportBody', reportId]`.
- **Finalize-while-saving race.** Disable Finalize during autosave;
  if a save fails, surface the autosave error before allowing
  finalize.
- **Manual edits regressed by AI.** Update prompt explicitly tells
  the model to preserve user-filled fields; verify via fixture +
  Maestro test.

## 7 — Out of scope

- Conflict resolution for multi-device editing of the same draft
  (last write wins for now; deferred until multi-author edit lands).
- Optimistic concurrency on `updated_at`. Single-user drafts only
  today.
